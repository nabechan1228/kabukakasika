## 2. セキュリティ脆弱性の修正

本システムを本番環境またはマルチユーザー環境で安全に動作させるため、重大なセキュリティリスクを排除しました。

### 2.1 SQLインジェクションの防止
- **課題:** バックテスト処理（`backend/backtest.py`）において、ユーザーが入力した銘柄コードなどをf-stringで直接SQL文に埋め込んでいました。
- **対策:** SQLAlchemyのプレースホルダーを使用したパラメータ化クエリ（`text("SELECT ... WHERE code = :code")`）へ修正しました。

### 2.2 入力値検証の徹底（不正入力と攻撃の排除）
- **対策:** APIへのリクエストパラメータ（銘柄コード `code`）に対して、`validate_stock_code()` バリデータを適用。
  - **バリデーションルール:** 日本の標準的な銘柄コードに対応する「**4桁の数字のみ** (`^\d{4}$`)」に合致しない入力は、即座に `400 Bad Request` とします。
  - **効果:** SQLインジェクション、OSコマンドインジェクション、不正なファイルシステムアクセス等の攻撃を API の玄関口で遮断します。

### 2.3 パストラバーサル（Path Traversal）の防御
- **課題:** モデルファイル（`.pth`）やスケーラー（`.json`）の読み書き・保存の際、クライアントから渡された銘柄コードがファイルパスに直接結合されており、`../` などの相対パス指定による任意ディレクトリのファイル改ざんや機密ファイル読み取りの危険がありました。
- **対策:** 
  1. 上記の `validate_stock_code()` によるバリデーション。
  2. パス生成時に `os.path.basename()` でファイル名のみを抽出し、あらかじめ指定した安全なディレクトリ配下のみを参照する設計（`get_model_path`, `get_scaler_path`）に変更。

### 2.4 重複実行・リソース競合の防止（学習処理のデデュプリケーション）
- **課題:** 同じ銘柄に対する学習リクエスト（`/api/train/{code}`）が同時に複数送られた場合、ファイルの競合やメモリ破壊、CPU負荷の異常上昇が起きる懸念がありました。
- **対策:**
  - スレッドセーフなグローバルなロック機構と、学習中ステータスを監視するスレッドセーフな辞書を導入。
  - 同一銘柄が学習中の場合、後続の学習要求を拒否する仕組みを追加。

### 2.5 内部情報の漏洩防止（エラーハンドリングの強化）
- **対策:**
  - APIのエラーレスポンスとして、Pythonのスタックトレースや詳細なエラー理由を直接クライアントに返さないように改善。
  - エラーの詳細はバックエンドのログファイルへ出力し、クライアントへは `「学習処理中にエラーが発生しました。ログを確認してください。」` のような抽象的なメッセージを返却します。

### 2.6 ネットワーク露出とCORSの制限
- **対策:**
  - **ホスト制限:** FastAPIの実行ホストを、外部のあらゆるPCから接続可能な `0.0.0.0` から、ローカルループバックアドレス `127.0.0.1` に変更（環境変数 `HOST` で変更可能）。これにより、意図せず外部ネットワークにサーバーが公開されることを防ぎます。
  - **CORS設定:** 許可するHTTPメソッドをワイルドカードの `["*"]` から、アプリに必要な最小限のメソッド `["GET", "POST"]` に制限。

## 3. 今後の開発・運用における注意点

1. **DBアクセス**: 新たにエンドポイントを追加する際は、必ず `backend/db.py` の `get_db` を使用してセッションを依存注入してください。
2. **バリデーション**: クライアントから受け取るすべての引数は、使用前にバリデーター関数を通してください。
3. **モデルやファイルの保存**: 任意のファイルを保存する場合は、必ず `os.path.basename()` などを通して、指定ディレクトリ外へのファイル出力（パストラバーサル）が発生しないようにしてください。
